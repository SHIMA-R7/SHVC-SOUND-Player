# バス切り替え診断（2026-10-02）

COM6、USB給電のみ、音量0、SPC700はIPL待機。曲実行はしない。

## 変更

SPC転送用のspc_bus.hだけを変更。GPIO番号は変更しない。
データ方向はpinMode、データ入出力はdigitalWrite/digitalReadを使用。
アクセスごとに/WR・/RDをHIGH、U2・U4のOEを両方HIGHにしてから方向を設定。
アドレス・データの準備後に対象のバッファだけ有効化。終了時に切り離す。
元のBLE MIDI用ヘッダーは変更していない。

0x0C診断コマンドを追加。ホスト入力ポート2/3に8パターンを書き、IPLの出力ポート0/1がAA/BBを維持するか512回読む。
転送開始のCCキックはしないので、SPCファイル転送アルゴリズムとは独立した診断。
応答は0C、GPIO flags、読出し不一致数LE16、D0～D7不一致数LE16（計20バイト）。
flags bit0は読出し後にデータGPIOの出力有効ビットが残っていた場合、bit1は読出し後のOE出力ラッチが両方LOWの場合。
flagsはソフトウェアの設定状態の観測で、実際の端子電圧やアクセス途中の波形を保証しない。

## 実機結果

| 試験 | 結果 |
| --- | --- |
| 読出しだけ128組 | 全てAA/BB |
| 切り替え試験1 | 512読出し中0不一致、flags=0 |
| 切り替え試験2 | 512読出し中0不一致、flags=0 |
| 切り替え試験3 | 512読出し中10不一致。全てD7、flags=0 |
| 最終リセット | AA/BB。音量0 |
| 改修後のSPC転送 | 先頭238バイトは成功。メインRAM204バイト目でCCが4Cと読まれ停止 |

ファームのGPIO設定を変更してもD7の間欠的な読出し不良は未解決。
この結果だけで基板・U4・給電・ファームのどれかに原因を断定しない。
次にU4の電源とD7経路、OE・/RDの実波形を確認する必要がある。
D7経路：SHVC-SOUND 14番 → U4 11番 → U4 9番 → ESP32 GPIO22。

再実行：`python tools/bus_diag.py COM6`。

## U4交換後の追加診断

ユーザーがU4を交換。今回の給電構成は再確認していない。
ファームは変更せず、既存のポート書込・読出しコマンドで実施した。

- 読取り128組、切替512回×3試行は不一致なし。
- SPC先頭238バイト転送は位置112で停止。期待70、実際6F。
- PCから1バイトずつ書くIPL試験でも位置176で停止。期待B0、実際AF。
  250ms内117回、追加32回、同じデータと番号の再書込後32回、全てAF。
- 18バイトのSPC診断プログラムを$1000へ転送・実行し、入力ポート0～2を
  各出力ポートへ連続コピー。固定マーカーは出力ポート3=D3。
  768比較×3試行の不一致は3、0、8。全てD4が1から0になる誤り。
- 14バイトの別プログラムで入力ポート0を出力ポート0～2全てにコピー。
  256パターン×3試行で、誤った入力パターン数4、0、3（出力比較数12、0、9）。
  例：入力30に対して出力3ポート全て20。入力72に対して全て62。
  追加読取りでも同じ値、同時に固定マーカーD3は正しく読めた。
  同値の再書込で復帰する場合としない場合がある。

単なるACK待ち時間やPCのまとめ送りでは説明しにくい。
固定値のD4は正しく読める一方、コピーした3出力のD4が揃って欠けるため、
書込み側D4経路が最も疑わしい。書込時の電圧・波形は未測定であり、
U2そのものの故障、接点、ESP32側の信号、制御タイミングまでは断定しない。

現行PCBパッドのネットを照合：GPIO18 → D4_3V3 → U2の6番入力 →
U2の14番出力 → SHVC_D4 → SHVC-SOUNDコネクタJ4の11番。
読取り側はU4の14番入力 → 6番出力で同じネットを読む。

診断コードの命令は[MAMEのSPC700実装](https://github.com/mamedev/mame/blob/master/src/devices/cpu/spc700/spc700.cpp)で照合。
DSPレジスタを書かず、曲は実行せず、試験後は音量0・リセットAA/BB。

再実行：`python tools/write_ack_diag.py COM6`、
`python tools/port_echo_diag.py COM6 --mirror`（SHVC-SOUND_pythonから実行）。

## U2交換後

ユーザーがU2を交換。同じmirror試験で768比較あたり3、135、272不一致。
試行1はD4のみ、試行2/3はD6のみ。試行3では書換えていない固定マーカーD3も
93と読まれる（例：42を送った時、マーカー追加4読取り全て93）。
そのため今回のD6誤りを入力側の書込みだけで説明できない。
U2単体故障という説明では不足し、共通データ線・読取り側・GPIO制御・電源を
含めて再評価する必要がある。D4の診断結果も書込み側確定とは扱わない。
続くリセット/IPL試験は128組AA/BB、切替512回×3全て不一致0、flags0。
IPLのAA/BBはいずれもD6=0なので、D6がHIGHを保てることを検証していない。
SPC全体転送は前提となるecho試験で不一致が出たため実施せず。
最終状態は音量0・リセットAA/BB。

## ESP32書込み端子診断（2026-10-03）

ユーザー測定：5V系4.55V、転送試行中もテスター表示は低下なし。
CH340はCOM15。診断コマンド0Dを追加し、ビルド・書込み・フラッシュ検証成功。
入力観測を有効にした診断モードで、$1000への開始要求4書込みについて、
WR前、WR LOW、WR HIGH、U2無効化後の4時点を記録。
各時点のGPIO出力ラッチ、ESP32端子の入力レジスタ、出力有効レジスタを返す。
診断の入力有効化と記録処理は通常転送に含まれず、厳密に同一のタイミングではない。

3試行全て16スナップショットに不一致0。
データ、アドレス、WR、RD、OE_W、OE_Rの期待論理値と出力有効状態が一致。
しかし3試行全てCC開始要求の応答なし、SHVC出力AA/BB/00/00。
ESP32端子の記録した論理状態は正常。全時間の波形、U2/U3後段の出力電圧や
SHVC内部への到達は、この診断では確認できない。
最終状態は音量0・リセットAA/BB。
再実行：`python tools/write_trace_diag.py COM15 --trials 3`。

### 判定

「ハードウェア的に通信不可能」「特定のICが故障」とは断定できない。
開始要求成功が126回あり、完全な断線や恒常的な無応答だけでは説明できない。
今回の全体転送成功は0/19。安定したSPC再生はまだできない。
接続の開き直しを境に成功・失敗が固まる場合があるが、全ての開き直しで
必ず失敗するわけではない。再起動・電源・初期化・信号レベルのどれに
由来するか、この結果だけでは区別できない。
ESP32端子の観測時点の論理値は正常で、単純な書込待ち時間延長では改善しない。
U2/U3後段・SHVC端子に届く電圧と波形は未測定。ファームの影響も完全には除外しない。
追加の同条件リトライだけではこの区別が進まないため、次はU3の16番
（SHVC_WR、SHVC5番へ接続）とU2出力の実測を優先する。

## WR静的測定モード

ユーザーがSHVCを抜いたソケット5番でWR待機HIGHを測定：4.63V。
LOW保持前の再測定4.63VはHIGH状態の測定であり、LOW側の結果ではない。
コマンド10＋level（0=LOW、1=HIGH）を追加。RESET・ミュートを保持し、
U2/U4のデータ出力を無効、RDをHIGHにしてWRを指定レベルで保持する。
応答は10、指定レベル、ESP32出力ラッチ、ESP32端子入力の4バイト。
`tools/hold_wr_diag.py COM15 --level low`は接続を開いたまま保持する。
標準入力へhigh/lowで切替、exitでHIGHへ戻して終了する。
この静的試験はU3の出力がHIGH/LOWを作れるかを見るもので、転送時の波形は保証しない。

WR LOW保持を実行後、ユーザーのソケット5番測定は0V。
同じ箇所のHIGH4.63Vと合わせ、無負荷でのWR静的HIGH/LOWは正常。
次のデータ静的試験用にコマンド11＋8bit値を追加。
RESET/ミュート保持、RD/WR HIGH、U4無効の状態でU2だけ有効にしデータを保持。
応答11、指定値、ESP32側出力ラッチの8bit値、端子入力の8bit値。
`tools/hold_data_diag.py COM15 --value 0`（対話端末で接続を維持）で全LOW、
highで全HIGH、0xNNで個別パターン、exitでデータ出力を無効化。
SHVCを外したソケット11番（SHVC_D4）で測る。
