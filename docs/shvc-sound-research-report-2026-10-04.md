# SHVC-SOUND-ESP32 研究・開発レポート

対象：SHVC-SOUND-ESP32 rev0.4。2026-10-04時点の組立・診断・ソフトウェア開発成果。外部アンプへのライン出力でSPC・MIDIの発音を確認し、Bluetooth保存とPCなしの再生を実現。内蔵アンプと最初の基板の故障原因は未解決。

[[TOC]]

## 1. 到達点と研究の目的

スーパーファミコンのSHVC-SOUND音源モジュールをESP32で駆動し、実チップによる音楽再生を行う。組立後は電源・音声回路と通信バスを別々に調べ、最終的に新しく組み立てた基板で通信と音声出力を成立させた。SPCのUSB転送、短いWAVのBRR再生、ESP32単体での起動、WindowsからのBluetooth制御とSPC/MIDI/WAV転送へ段階的に拡張した。

本レポートは会話中のユーザー測定・可聴確認、保存した試験ログ、現行PCB・BOM、実装コードをまとめた記録である。「成功応答」「音が聞こえた」「原因を特定した」は別の結果として扱う。追試可能な証拠を残し、過去の推測を確定事実へ置き換えない。

現在はSimCityのMegalopolisを保存し、給電を続ければPCを切り離しても音源側で曲が動く構成になっている。PC停止後にUSB給電も止まる環境では別電源が必要。元のSPCの曲プログラムが持つループを使い、ホストによる時間制限やフェードを加えない。任意の終了曲を強制ループへ変える処理ではない。

## 3. アンプ電源の発熱と音声経路

### 3.1. R10発熱の観察と残る疑問

電源投入でR10が焦げ、コンデンサを切り離した後も発熱した。さらにU6を外した条件でも発熱したとの報告がある。一方、U6の出力脚をソケットから離し、抵抗・コンデンサ・アンプを組み戻した後には発熱しないと確認された。これは有効だった実装変更の記録であり、過去の全条件を再現して原因を確定した試験ではない。

現行PCBではU6の反転出力に相当するソケット端子がGNDへつながっている。TDA7053Aのメーカー資料では該当端子は出力であり、通常のBTL出力をGNDへ短絡する接続は再検討が必要。メーカーはヘッドホン向け単端接続を限定的に認めているが、反転出力のGND短絡を正当化する説明ではない。ここはピン配置と使用条件を確認して設計を改める対象である。参照：資料[1]のピン表・機能説明。

**原因未確定**：U6不在でも発熱したという観察は、出力短絡だけでは説明しきれない。試験時の配線状態、電源側の別経路、実装の変化などを再構成する必要がある。コンデンサだけ、アンプだけ、ガーバーだけの問題と断定しない。次回は電源を切った状態のネット確認と、電流制限下でのR10両端電圧・電源電流の測定を記録し、実装条件ごとに比較する。

| 観察対象 | 記録された結果 | 判断 |
| --- | --- | --- |
| R10発熱 | C3/C4を外しても発熱したとの報告 | コンデンサ単体だけを原因にはできない |
| U6を外した試験 | それでも発熱したとの報告 | 後の出力脚対策だけでは全履歴を説明できない |
| U6の刻印 | 写真ではTDA7053、Aの刻印を確認できず | 発注名TDA7053Aと実物の違いを重視 |
| U6出力脚の処置 | 12/13番をソケットへ挿さず、部品を再組立 | その後、R10が発熱しないとユーザー確認 |
| 第1基板のD4 | HIGH保持で約2.6 V、U2を浮かせた点で約4.58 V | 負荷・接点・基板配線を疑うが原因未確定 |
| 第1基板の抵抗測定 | U2ソケット6番と14番の間で約165 Ωの記録 | 測定状態・他経路を含み、不良部位を確定しない |
| 5V系の測定 | 約4.55 V、転送中の表示低下なし | テスターでは短時間の電圧低下を排除できない |
| 第2基板 | 再組立後に全SPC転送が連続成功 | 同じソフトで改善。第1基板の故障点は未同定 |
| ライン用コンデンサ | SHVC音声側の左右DCは約+1.32 V | 実装判断の参考。交流の全波形・全条件は未測定 |

### 3.2. アンプを迂回して発音を確認

基板想定のA付きと現物のAなしでは入力配置が異なるため、音量制御と思った端子の電圧だけで正常動作を判断できない。最終的な発音確認は内蔵アンプを迂回し、外部アンプのライン入力へつないで実施した。ジャンパを残したままU6を挿入しない。これは外部アンプ向けの経路であり、イヤホンを直接駆動した確認ではない。

| 経路 | 現行PCB上の接続 | 扱い |
| --- | --- | --- |
| J5 | 1=LINE_L / 2=GND / 3=LINE_R | C14/C15経由、U6を通らない |
| J1の左迂回 | U6ソケット4 → 9 | U6を抜き、外部アンプのライン入力へ |
| J1の右迂回 | U6ソケット6 → 16 | 左右の実接点は現物で導通確認 |
| U6ソケット12 / 13 | GND / GND | 元PCBの接続。アンプ再実装時は再検討 |
| アンプPWM | GPIO33 = 0 | 今回の発音確認では内蔵アンプを制御しない |

## 4. 通信不良の切り分けと再組立の結果

### 4.1. 最初の基板で分かったこと

リセット後のIPL応答が正常でも、任意のデータが正常に届くとは限らなかった。AA/BBに含まれないHIGHビットは、その応答だけでは検証できない。短いコピー用SPC700プログラムを用い、送った値と返った値を比較したところ、書込側D4を疑う結果があった。その後は固定マーカーにもD6誤りが現れたため、書込側だけの問題という仮説を撤回して共通経路を再評価した。

ESP32端子の論理観測では全データ値が一致したが、後段の電圧や全時間の波形までは確認できない。書込パルスを延長しても全体転送は改善せず、単純な待ち時間不足だけでは説明できなかった。ICやSHVCモジュールの交換だけでも安定しなかった。静的測定中は接続を開いたまま保持し、USB抜き差し・リセット後に古い保持状態を前提としない運用へ改めた。

| 試験 | 記録 | 限界・解釈 |
| --- | --- | --- |
| 開始要求の反復 | 100回成功＋端子記録付き20回成功 | 完全な恒常断線という説明は不十分 |
| 接続開き直し | 6/6成功の接続と0/6の接続があった | 初期化・電源・信号などを区別できない |
| 最初の全体転送反復 | 標準・延長条件を合わせ0/19成功 | 曲の安定再生は成立しなかった |
| データ端子試験 | 256値×5回、1280観測で不一致なし | ESP32の観測時点の論理値のみ正常 |
| WR静的試験 | HIGH約4.63 V / LOW 0 V | 無負荷の静的試験。転送波形を保証しない |
| DRC確認 | 未接続項目0、電気的短絡の指摘なし | ネットリスト整合性は機能設計や実物無短絡を保証しない |

## 5. ソフトウェア成果とBluetooth拡張

### 5.1. USB転送とPCなしの起動

SPC転送用ファームはバッファの両OEを無効化してから方向を変え、アドレス・データ設定後に対象バッファだけを有効にする。診断用コマンドでGPIO観測、書込時間変更、全値試験、静的保持を追加した。既存AVRのPCMストリーミングと同じ番号でも意味が異なるため、ツールの互換性を前提にしない。

SPCはRAMを転送し、DSP・タイマー・CPU状態を復元するコードを実行して曲へ戻る。SimCityではIPL転送用の入力ポート値がゲーム側の指示として誤解釈され得るため、復元コードとホストのハンドシェイク後に保存値へ戻す。単体版はこの処理と曲データをESP32フラッシュへ組み込み、起動時に自動転送する。起動ログのIPL、全ブロックACK、PLAYINGとユーザーの音声確認が得られた。

USB転送による短いWAVはモノラル化・リサンプル・BRR変換をPCで行い、サンプルと専用DSP初期化コードを送る。約11秒のモーニングコールを可聴確認した。

### 5.2. Bluetooth版の構成

WindowsのTkinter画面またはCLIからBLEの独自制御サービスへ指示を送る。同時に標準BLE MIDIサービスを設け、リアルタイムMIDIを受信する。BLEコールバックではキューへ追加するだけとし、SHVCバス操作とファイル操作はメイン処理側にまとめた。SPC曲とMIDIシンセは同じ音源を使うため、演奏モードを切り替える。

曲はLittleFSの別スロットへ候補として受信し、転送位置、CRC、サイズ、曲形式を検証してからNVSの有効スロット参照を更新する。途中切断や検証失敗時には前の正常保存曲を保持する。リセット後に保存曲を再生することまで確認した。Windows GUIには再生・停止・mute、MIDIの全体音量・チャンネル音量・パン・Expression・音色・サステイン・Pitch Bendを用意した。

| 機能 | 実装・制約 |
| --- | --- |
| SPC | Windowsで復元コードを作り、RAMとまとめて保存・送信。元の曲のループを使用 |
| MIDIファイル | Windowsでテンポマップを解決し、時刻付きイベントとして保存。ESP32で演奏 |
| リアルタイムMIDI | 標準BLE MIDI。8ボイス、既存GM・ドラム音色マッピング |
| WAV | 16-bit PCMをBRR化。短い音声を一括保存・1回再生。内部形式はSPC用HSP1 |
| ファイル保存 | 最大256000バイト。有効曲1つと候補1つ |
| MIDI上限 | 30000イベント / 24時間。タイプ0・1、タイプ2は対象外 |
| WAV上限 | 8 kHzモノラルで約14秒、32 kHzで約3.5秒。GUI既定は先頭10秒 |
| フラッシュ区分 | アプリ3 MB / LittleFS 896 KB、OTA用第2アプリなし |
| 転送保護 | 位置・CRC32・形式確認、30秒受信停止と切断で未完了受信を破棄 |
| 接続 | 1クライアントを想定。ペアリング・暗号化は要求しない |

### 5.3. 実機・オフライン検証

Bluetoothのmute切替、MIDIのライブノート、音量・CC・音色、保存MIDIの演奏と末尾停止が成功した。ユーザーはド・ミ・ソを可聴確認した。不正offset、CRC不一致、途中切断の各試験でも前の保存曲が残った。Megalopolisの保存・復元とリセット後の自動再生が成功し、ユーザーは曲が聞こえることを確認した。最終ファームではMIDIファイル演奏中のExpression・サステイン・Pitch Bendも受け付ける処理を検証した。

Bluetooth経由のWAVは保存と再生開始の成功応答まで確認した。今回のWAV自体の音声についてはユーザーの返答がまだなく、USB転送での過去の可聴確認と混同しない。オフラインの回帰テストではMIDIテンポ変更、タイプ2拒否、最小MTUでの分割・CRC、状態flags、WAV配置・終端フラグ・入力形式・RAM上限の検証が成功した。操作画面の初期化・終了とWindowsでの表示も確認した。

## 6. 未解決事項と次の検証

**未検証**：内蔵アンプの正常発音。出力脚の接続とA付き/Aなしの配置を再設計・照合し、電流制限とダミー負荷で検証する。実証済みの外部アンプへのライン出力を当面の運用経路とする。

**原因未確定**：旧基板の通信不良と、U6を外してもR10が発熱した条件。電源構成、実装状態、測定点の向きを写真・回路図で固定し、問題条件を再現できる記録にする。オシロスコープによる後段の信号と給電波形の確認が次の切り分けとなる。リトライ回数だけを増やして故障箇所を決めない。

**既知の制約**：SPC復元コードがRAM上部を上書きするため、そこに曲データやエコーがある曲では破綻し得る。既存の配置を汎用保証とは扱わず、小型化または配置戦略を検討する。SPCの音量倍率は復元時のDSP初期値だけを変え、曲がレジスタを書き直すと効果が変わる。汎用的なリアルタイム音量・テンポ変更は未実装。

**未対応**：長いWAVの連続ストリーミング、WAVのシーク・一時停止・自動ループ。長音声が必要なら現在のRAM一括方式とは別の転送方式を検討する。密集したMIDIイベントはバス処理による遅延があり、厳密なサンプル同期ではない。

**未検証**：長時間のループ耐久、頻繁なパラメータ変更、他OS、BLE MIDI専用アプリ、複数台接続、PCの実シャットダウン時の電源挙動。別電源による給電を確認し、接続・切断・再起動・長時間演奏を条件ごとに記録する。曲の生成ヘッダーと曲入りバイナリは著作物を含むため公開対象から外している。

## 7. 現在の操作と確認状況

WindowsではSHVC-SOUND_python/start_ble_player.cmdで操作画面を起動できる。Bluetoothを有効にし、「Bluetooth接続」からSHVC-SOUND Playerを検出する。「SPC / MIDI / WAVを選ぶ」から「送信して再生」を実行する。SPCやWAVはESP32保存後に音源側へRAMを転送するため、保存完了から発音まで待ち時間がある。MIDIモードへの切替でも音色バンクの転送が入る。

WAVは先頭の指定秒数を使用し、再生が終わると無音になる。「保存曲を再生」で再び鳴らせる。最後の試験後はMegalopolisを保存曲へ戻し、自動再生を有効にした。Bluetooth版のシリアルは診断ログ用であり、従来のSPC GUIのバイナリ転送を使うにはUSB転送ファームを書き戻す。
